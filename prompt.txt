# CATALOGIST — MASTER DEVELOPMENT PROMPT

## 1. Project Identity

Project name: **Catalogist**

Purpose: A professional, modular, secure, extensible WordPress/WooCommerce plugin for creating printable product catalogs.

Slug / Text Domain:

```text
catalogist
```

PHP Namespace:

```php
Catalogist\
```

Function / Hook Prefix:

```text
catalogist_
```

Catalog CPT:

```text
ctlg_catalog
```

Template CPT:

```text
ctlg_template
```

# 4. Fundamental Development Philosophy

Catalogist must be developed using:

## Progressive Architecture

and

## Vertical Slice Development

The target architecture defines the direction of the product.

The current Stage defines what may actually be implemented.

Do not attempt to build the entire architecture before the implementation requires it.

Prefer:

```text
Small Requirement
    ↓
Small Design
    ↓
Implementation
    ↓
Test
    ↓
Review
    ↓
Validated Architecture
    ↓
Next Requirement
```

over:

```text
Complete Architecture
    ↓
Complete Infrastructure
    ↓
Complete Implementation
    ↓
Testing at the end
```

---

# 5. Target Architecture vs Current Architecture

Always distinguish between:

### Target Architecture

The architecture Catalogist is expected to evolve toward.

and:

### Current Architecture

The architecture that actually exists and is justified by the current implementation.

The Target Architecture is a direction.

It is NOT permission to create every future class, interface, service, repository, adapter, directory, or abstraction immediately.

---

# 6. Non-Negotiable Scope Rule

## Current Stage Only

You may implement only functionality required by the current Stage.

Future functionality may be:

* documented
* referenced
* considered in architectural decisions

but must not be implemented prematurely.

For example, if the current Stage concerns Catalog persistence:

Do NOT implement:

* Product Query Engine
* Variation Engine
* Template Engine
* Elementor integration
* Print Engine
* Preview Engine
* PDF generation

unless explicitly required by the current Stage.

If you discover that future functionality would require changes to the current design, document the issue instead of silently implementing future infrastructure.

---

# 7. Anti-Overengineering Rule

Do not create abstractions merely because they may be useful in the future.

Avoid unnecessary:

* interfaces
* abstract classes
* factories
* repositories
* service layers
* providers
* adapters
* containers
* event systems
* caching layers
* infrastructure

unless the current Stage provides a concrete reason for them.

Use SOLID and other architectural principles pragmatically.

An abstraction must solve a real problem.

Do not create an interface solely because:

> "There may be another implementation later."

When one implementation is sufficient, a simple implementation is preferred unless there is a clear architectural reason otherwise.

# 9. WordPress Principles

Use WordPress-native APIs and conventions whenever appropriate.

Prefer:

* WordPress APIs
* Custom Post Types
* Post Meta
* Options API
* Transients / object caching where justified
* Settings API
* REST API
* WordPress capabilities
* Nonces
* WP Cron where appropriate
* WordPress hooks
* WordPress internationalization

Do not create custom infrastructure when WordPress already provides a suitable mechanism.

Use custom database tables only when a demonstrated requirement or measured performance problem justifies them.

---

# 10. WooCommerce Principles

Catalogist must integrate with WooCommerce through supported and stable APIs.

Do not duplicate WooCommerce's product data model unnecessarily.

Product access must be designed to avoid:

* N+1 queries
* repeated product loading
* unnecessary metadata queries
* redundant API calls

Catalogist should remain compatible with modern WooCommerce architecture and should not make assumptions that unnecessarily interfere with WooCommerce features such as HPOS.

WooCommerce must be treated as an external domain dependency of Catalogist.

# 13. Catalog Model

Catalogist will eventually support catalogs containing structured configuration such as:

* Product query
* Filters
* Selection
* Sorting
* Variation selection
* Template
* Layout
* Print settings
* Output settings
* Version information
* Status

Catalog data must be stored structurally.

Do not store business configuration as generated HTML.

Where appropriate, use:

* CPT
* structured post meta
* Options
* cache

---

# 14. Catalog Items

Products and variations should eventually be normalized into a Catalogist Catalog Item representation.

Conceptually:

```text
WooCommerce Product / Variation
        ↓
Catalog Item
        ↓
Template Context
        ↓
Renderer
```

Templates should not become tightly coupled to direct WooCommerce API calls.

The Catalog Item should expose the normalized data required for rendering.

Implement this only when the current Stage requires it.

---

# 15. Standard Context

The long-term standard rendering context is:

```php
[
    'catalog'   => $catalog,
    'item'      => $catalogItem,
    'product'   => $product,
    'variation' => $variation,
]
```

This Context is a shared architectural contract.

Elementor, templates, widgets, dynamic tags and renderers should consume the same conceptual data model where applicable.

---

# 16. Product Query Engine

The final Product Query Engine may support:

* Product IDs
* Categories
* Tags
* Custom taxonomies
* SKU
* Product type
* Status
* Stock status
* Price
* Date
* Search
* Other justified WooCommerce criteria

The engine must support composable filtering.

Example:

```text
Category A
AND
(Tag X OR Tag Y)
```

However, filters should be introduced progressively.

Do not implement every filter in one Stage unless explicitly required.

---

# 17. Sorting

The final system may support:

* Date
* Title
* Price
* SKU
* Menu order
* ID
* Custom ordering
* Other justified strategies

Sorting should be extensible without unnecessary abstraction.

Implement strategies progressively.

---

# 18. Variation System

Catalogist will eventually support multiple variation-selection modes, including:

1. Parent product only
2. All variations
3. Manual variation selection
4. Multiple selected variations
5. Parent with variation information/table

Variation handling must be explicit and predictable.

Do not build all modes simultaneously unless the current Stage requires them.

---

# 19. Template System

Templates must be independent from Elementor.

The long-term conceptual model is:

```text
Template
├── Header
├── Product Loop
│   └── Product Card
└── Footer
```

Templates should consume Catalogist Context.

Elementor may provide a visual editing layer but must not become the underlying business logic of Catalogist.

---

# 20. Elementor Integration

Elementor is optional.

Catalogist Core must function correctly when Elementor is:

* not installed
* inactive
* unavailable
* upgraded independently

Elementor functionality must live behind an integration boundary.

Possible future integrations include:

* Widgets
* Dynamic Tags
* Template integration
* Controls
* Editor integration

Do not implement Elementor functionality before the Core contracts it consumes are sufficiently stable.

---

# 21. Rendering Separation

Maintain separation between:

```text
Data
 ↓
Context
 ↓
Renderer
 ↓
HTML
 ↓
Print / Preview / Output
```

Do not mix:

* WooCommerce data access
* Elementor-specific logic
* print logic
* output logic

inside a single component.

---

# 22. Print Architecture

The final Print Engine should support:

* A4
* margins
* page dimensions
* print CSS
* page breaks
* repeated headers/footers where appropriate
* avoiding unwanted product-card splitting
* RTL/LTR
* browser print

Use CSS print mechanisms where appropriate:

```css
@media print
```

and suitable page-break / break-inside rules.

Print implementation should remain separate from normal web presentation.

---

# 23. Preview

Preview should reflect the actual rendering pipeline as closely as practical.

Avoid creating a completely separate rendering system for Preview.

Prefer:

```text
Same Data
    ↓
Same Context
    ↓
Same Renderer
    ↓
Preview / Print / Output
```

---

# 24. Output

The initial output target is:

```text
HTML + Browser Print
```

PDF support should be architected through an abstraction/provider model only when justified.

Do not introduce a hard PDF dependency into the Core MVP.

---

# 25. QR Codes

QR functionality should eventually use a provider-based design where justified.

Core should not become dependent on a specific QR library unless there is a concrete requirement.

---

# 26. Custom Fields

Custom field support should be extensible.

Potential providers may include:

* WordPress custom fields
* ACF
* JetEngine
* Other supported providers

Do not create integrations before there is a concrete requirement.

# 27. Security

Security is not a final-stage activity.

Security must be considered in every Stage.

Always apply where relevant:

* capability checks
* authorization
* nonce verification
* input validation
* sanitization
* output escaping
* safe SQL/query usage
* safe REST handling
* safe AJAX handling
* safe file handling
* safe URL handling
* prevention of privilege escalation
* prevention of unintended data exposure

The final project must also receive a dedicated security audit.

---

# 28. Performance

Performance must influence architecture from the beginning.

Target:

```text
500–1000 products
```

Avoid:

* N+1 queries
* repeated WooCommerce object loading
* redundant meta queries
* unnecessary REST requests
* excessive DOM generation
* unnecessary repeated computation

Caching should be introduced when justified by:

* measured performance
* concrete architecture requirements
* repeated expensive operations

Do not build elaborate caching infrastructure merely because the system might need it later.

---

# 29. Admin Architecture

The Admin UI should evolve with the actual functionality.

Do not build the complete administration interface before the underlying feature exists.

Use WordPress-native admin mechanisms where appropriate.

The UI should prioritize:

* clarity
* predictable behavior
* minimal unnecessary complexity
* accessibility
* security
* RTL compatibility

---

# 30. REST / AJAX

REST/AJAX should be used when the UI genuinely requires interactive communication.

Business logic must remain outside controllers.

Prefer:

```text
REST Controller
    ↓
Application / Service Logic
    ↓
Domain / Repository
```

where such layers are actually justified.

Do not duplicate business logic inside REST endpoints.

---

# 31. Error Handling

The plugin must fail safely.

Account for conditions such as:

* WooCommerce inactive
* Elementor inactive
* missing catalog
* deleted product
* deleted variation
* invalid template
* missing image
* invalid configuration
* unauthorized request
* malformed REST request
* unavailable dependency

Errors should be explicit, actionable, and safe.

Do not expose sensitive internal information to users.

# 37. Stage System

The project is developed through **Stages**, not Milestones.

Each Stage must represent a small, meaningful, verifiable increment.

A Stage should preferably produce a working vertical slice.

Example:

```text
WordPress
    ↓
Catalogist Bootstrap
    ↓
Catalog CPT
    ↓
Create Catalog
    ↓
Save Catalog
    ↓
Load Catalog
    ↓
Tests
```

This is preferable to creating large isolated infrastructure layers with no working feature.

### Architecture

* hack
* temporary workaround
* poor architecture
* duplicated logic
* unsafe implementation

```text

    ↓

    ↓
Decision
    ↓
Implementation
    ↓
Verification
```

# 44. Regression Protection

Every Stage must verify that previously completed functionality still works.

A Stage is not complete if:

```text
new feature works
BUT
old feature breaks
```

The previous Stage becomes part of the regression baseline.

---

# 45. Stage Gate

A Stage can be considered complete only when:

```text
[ ] Goal achieved
[ ] Scope respected
[ ] Acceptance criteria satisfied
[ ] Tests pass
[ ] Regression checks pass
[ ] Security reviewed
[ ] Architecture reviewed
[ ] No unnecessary implementation remains
[ ] Documentation updated where necessary
[ ] Git checkpoint created
```

Only after all applicable criteria are satisfied may the Stage be considered complete.

---

# 46. Architecture Drift Review

At the end of each Stage, review:

* Did implementation remain compatible with the Target Architecture?
* Did we introduce unnecessary coupling?
* Did we create premature abstractions?
* Did the Stage accidentally implement future functionality?
* Did WordPress/WooCommerce responsibilities remain clear?
* Did Elementor remain optional?
* Did the implementation become more complex than necessary?

If architectural drift exists:

1. identify it
2. explain it
3. correct it if it belongs to the current Stage
4. otherwise document it

The new project must explicitly avoid:

### Big-Bang Architecture

Do not design and implement the entire system before validating the foundation.

### Premature Abstraction

Do not create large abstraction trees before real requirements exist.

### Scope Explosion

Do not allow a Stage to silently absorb future features.

### Feature-Claim Inflation

A feature is not implemented because:

* a folder exists
* a class exists
* an interface exists
* a placeholder exists
* a README claims it exists

A feature is implemented only when it is:

```text

+
Integrated
+
Tested
+
Verified
```

### Testing at the End

Testing must occur continuously.

### Security at the End

Security must be considered continuously.

### Full File Structure Too Early

Do not create future modules simply because the Target Architecture contains them.
